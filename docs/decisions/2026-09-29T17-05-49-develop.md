## 1. Decision

1. `models.WriterOutputSchema`（`additionalProperties` を含む JSON Schema）は、`generationConfig.responseJsonSchema` へ載せる。OpenAPI subset 用の `responseSchema` は使わない。
2. `responseMimeType=application/json` は引き続き必須。`responseJsonSchema` と `responseSchema` は排他なので、同時に送らない。
3. 先行 Decision（`2026-09-29T02-10-39-cursor-gemini-structured-yesterday-window-6a75.md`・`2026-09-29T04-53-13-cursor-gemini-structured-yesterday-window-6a75.md`）の「`responseSchema`」は、この判断で「`responseJsonSchema`」に置き換える。schema を型から生成する方針・TextWriter だけが structured 拘束を持つ方針は維持する。

## 2. Reason

1. 本番 System test（run 36538248785）が、Gemini から `400 INVALID_ARGUMENT: Unknown name "additionalProperties" at 'generation_config.response_schema'` を受けた。
2. 公式 REST reference の `Schema` object（`responseSchema` の型）は OpenAPI 3.0 の subset で、`additionalProperties` を持たない。一方 `responseJsonSchema` は JSON Schema を受け、`additionalProperties`・`required`・`items` を対応 keyword に挙げている。生成する schema の記法は JSON Schema なので、載せる先を `responseJsonSchema` にすると request が仕様どおりになる。
3. fake の HTTP round tripper を使う Unit / Narrow Integration は、Gemini が field を受理するかを検証できない。受理の確認は credential 付きの System test だけが持つ。

## 3. Rejected

1. **`additionalProperties` を消して `responseSchema` を維持する案** — 400 は避けられるが、余分な key を許す弱い拘束になる。しかも公式が deprecated と記す field に残る。
2. **`responseFormat.text.schema`（新形式）へ移す案** — 公式が `responseSchema` の後継として挙げるが、enum 値の表記や v1beta での実挙動を実 API で確かめていない。未検証の形式へ同時に切り替えると、失敗時に原因を切り分けられない。
3. **schema を OpenAPI subset へ変換して `responseSchema` に載せる案** — 型から生成する schema の第二の記法・変換層が増え、SSoT が割れる。
