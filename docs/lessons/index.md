- 2026-09-07 [fix/playback-e2e-test] 障害調査で「最有力の原因」を宣言する前に、その候補を確定 or 棄却できる一次観測（server log・実 request の応答 body）を先に取る。候補を確度順に並べる作業と、決定的な log を 1 本引く作業では後者を優先する。外形（test の失敗 locator）だけで原因を推論して確度を付けると、実 log が別方向を指したとき（例: session 生存を示す header が付いていた）に手戻りする  # → layer:workflow
- 2026-09-07 [fix/playback-e2e-test] 外部 API 認証の失効を疑うとき、失効の HTTP status を仕様で確認してから犯人を名指しする。token 失効は 401、request 内容不正は 400 のように意味が分かれる。status を見ずに「token 切れ」と断定すると、同じ status を返す別原因（設定値の不正など）と混同する。加えて、その API client の共通 request 経路が複数種類の呼び出しを 1 つの error message へ畳んでいると、status だけでは呼び出し種別を切り分けられない。畳み込み経路には呼び出し種別の label を必須引数で持たせ、log から一次切り分けできる粒度にする  # → layer:terms
- 2026-09-07 [fix/playback-e2e-test] flow 指示（例: 「success したら deploy → commit → …」）の実行中に分岐点へ来ても、選択肢が git 履歴で復元可能な範囲なら user へ質問せず自律判断で進める。質問して turn を止めてよいのは、判断材料が本当に不足し、かつ不可逆な副作用に関わるときだけ。flow の完遂責任を「確認を挟む」で薄めない  # → layer:workflow
- 2026-09-08 [feature/generator-text-writer-fallback] 定数（外部 API の model 名・endpoint・閾値）の値は宣言 1 箇所を SSOT にし、docs（Decision・進捗 index・lane）はその識別子を参照するだけにする。docs に値そのものを写すと、版更新のたびに複数箇所の追随が要り、片方だけ古くなる。「なぜその値か」の理由は docs に残してよいが、値そのものは残さない  # → layer:terms
- 2026-09-08 [feature/generator-text-writer-fallback] 委譲先（subagent）の self-report や、過去の別 session が残した commit message の主張を、最終状態の根拠にしない。「消えたのは事故」「union で復元した」等の要約は当時の判断であって事実の確定ではない。conflict や欠損を解消する前に、その path の全履歴を遡り、各 commit の diff と親を実際に見て、誰がいつ何行をどう変えたかを一次情報で組み立てる  # → layer:workflow
- 2026-09-08 [feature/generator-text-writer-fallback] 3-way merge で片側が「ほぼ空のファイル」を起点に大量 append、もう片側も別内容を大量 append していると、ほぼ全行が conflict になる。行数の大きな乖離（253 行 vs 5 行等）を見たら「単純 union で全部残す」を反射的に選ばず、まず merge-base 時点のファイル内容を確認する。base が空なら、どちらかの系列が過去に内容を失っている可能性があり、union は失われた内容を復活させる副作用を持つ  # → layer:platform
- 2026-09-08 [feature/generator-text-writer-fallback] 外部サービスの仕様（利用可能な model・API バージョン・料金）を答える前に、自分の知識の cutoff を意識し、公式 docs / API の一次確認を後回しにしない。「一般に GA な一覧」は知識で言えても「この key/project でその識別子が解決するか」は動的で、API に問い合わせるか公式ページで裏を取るまで確定しない。古い識別子は 404/NOT_FOUND として現れ、smoke test がそれを検出する  # → layer:platform
- 2026-09-08 [feature/generator-text-writer-fallback] 「この失敗は原因 X だから対処 Y にすべき」と分岐条件を決める前に、X を確定 or 棄却できる一次観測（エラー応答の body・code）を取る。取るための診断（応答本文の bounded snippet を error に載せる等）を先に実装してよい。外形（HTTP status だけ）で条件を決めると、同じ status の別原因を取りこぼす。status の意味が仕様上分かれる場合はなおさら body の code まで見て分岐する  # → layer:terms
