## 1. 目的（WHY）

- 毎日の IT ニュースを、日本語の podcast として自動生成・保存し、スマホからいつでも聴ける個人利用の仕組みを作る。
- 商用サービスではない。個人利用。
- 本企画の最終形は段階的に作る。本 PROPOSAL の実装ゴールは「全システムをモックで実装した MVP」とする（§4）。

---

## 2. 全体アーキテクチャ

3 つの責務に分割し、横断してオーケストレーションが制御する。

- podcast 出力システム（毎日 cron 実行を想定）。内部はさらに以下のサブシステムに分割する:
  - 情報取得システム（情報源ごとに別ロジック。入力は多様、出力は指定形式のテーマ情報テキスト。1 入力から複数テーマもありうる）
  - テーマ単位原稿生成システム（入力: 指定形式のテーマ情報テキスト → 出力: 指定形式の数分尺のテーマ原稿）
  - 原稿生成システム（情報取得とテーマ原稿生成を統合し、原稿.json を組み立てる）
  - TTS システム（原稿.json → 音声 → 結合 → Drive 保存）
- 再生 UI（スマホファースト、Vercel デプロイ想定）
  - podcast 一覧表示・再生・原稿表示・原稿内テキストのタップ意味検索
- オーケストレーション（横断）
  - 設定管理 + 依存性注入による各システムの起動・連結 + cron 定期実行制御
  - 各システムへ設定を注入してインスタンスを起動するイメージ（DI）

### 2.1 基盤構成

- 出力システムの定期実行基盤と再生 UI 基盤は別基盤に分離する（ロジックをインフラに依存させない）。
- ただし両者は同一 project 内の共通設定ファイルを参照する。

### 2.2 原稿.json 形式（MVP では仮置き）

- timestamp
- 本体: { 最初のまとめ, [ テーマ1の原稿, テーマ2の原稿, ... ], 最後のまとめ }

---

## 3. 制約条件

- 個人利用。public 公開しない。Drive・UI は自分の Google アカウント login 前提。
- 独自の DB / インフラを持たない（生成物は外部サービス＝Drive に保存）。UI は静的、DB なし。
- TTS は gemini-flash を用いる。
- API provider（原稿生成・TTS 等）は変わりうる前提で構成する（差し替え可能に）。
- production branch への push 禁止・deploy 禁止（deploy は shim が将来行う）。詳細は `WORKFLOW.md` §7。

## 4. MVP（実装ゴール）

### 4.1 MVP の定義

全システムをカプセル化し、固定レスポンスのモックで実装する。オーケストレーションが設定／依存性注入により各システムを起動・連結し、以下が end-to-end で繋がることを確認する:

- 入力(手動 text モック)
- → テーマ原稿生成(モック)
- → 原稿.json 組立
- → TTS(モック)
- → Drive 保存(モック)
- → UI 表示(モック)

外部 API・ロジック・原稿・UI はすべてモック。目的は、各システムを分離・カプセル化し、非機能要件を満たす構成になっているかの確認。

### 4.2 モックの方針

- 各モックは「指定形式に準拠した、もっともらしいダミーデータ」を返す（形式だけ本物・中身はダミー）。
- 原稿.json の形式は §2.2 を仮置きとして採用する。

### 4.3 MVP スコープ外（将来スコープ）

以下は MVP では実装せず、将来スコープとして区別する:

- 実 API の繋ぎ込み（原稿生成・TTS 等）
- 各情報源の本実装（手動 text 以外: Twitter 非公式 API・Mastodon 公式 API・IT ニュースフィード 等）
- テンプレート原稿適用ロジックの本実装
- cron の実稼働
- deploy / 本番反映

## 5. 受け入れ条件（ACCEPTANCE CRITERIA）

二値判定可能なチェックリストで表す。

### 5.1 機能要件（システム連結の確認）

- [ ] オーケストレーションが共通設定ファイルを読み、各システムへ設定を注入して起動できる。
- [ ] 入力(手動 text モック) → テーマ原稿生成(モック) → 原稿.json 組立 → TTS(モック) → Drive 保存(モック) → UI 表示(モック) が end-to-end で 1 本通る。
- [ ] 各システム境界が test で検証され、モック入出力が次システムへ正しく渡ることを確認できる。
- [ ] 再生 UI（モック）で、podcast 一覧表示・再生・原稿表示・原稿内テキストのタップ意味検索（タップでポップアップに意味の検索結果を出す）が動作する。
- [ ] 再生 UI は Drive 上のフォルダ走査でエピソード一覧を取得する構造になっている（モック）。

### 5.2 設定／依存性注入（オーケストレーションの確認）

オーケストレーションが注入・管理できること:

- [ ] 尺（5〜30 分の範囲指定）
- [ ] 話者モード（1 人ニュース風 / 2 人対話）。初期既定は 1 人ニュース風。
- [ ] 情報源の有効/無効（初期は手動 text のみ有効、他はモック interface）
- [ ] 出力システムへ「何を込めるか」（どの情報取得・原稿生成システムを注入するか）
- [ ] テンプレート原稿の選択口（選択キーのみ用意、適用はモック）
- [ ] API provider 選択（原稿生成・TTS の差し替え口）
- [ ] Drive 保存先
- [ ] cron 有効/無効

### 5.3 非機能要件（構成レベルの確認）

- [ ] 各システムが独立差し替え可能（他システムを書き換えず 1 つをモック差し替えできる）＝ 移植性・拡張性
- [ ] システム境界が interface で分離されている ＝ カプセル化
- [ ] API provider の差し替えが設定／注入経由で、コード変更最小で可能 ＝ 拡張性・移植性
- [ ] 各システムが単体 test できる ＝ 保守性・信頼性

### 5.4 主観判定項目

- 「日本語の自然さ」「ニュース風の簡潔さ（冗長な導入・小噺なし、事実を簡潔に）」「固定構成の妥当性」などの主観項目は、MVP では原則モックのため判定不要。判定できない／不要な場合は無視してよい。
- 番組の固定構成（オープニング有無・トピック順・各トピック=サマリー→解説・クロージング有無）はこの主観枠で扱う。
